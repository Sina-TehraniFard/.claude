# /c-advance-task

ワークスペースのタスクを、受け取ってから完了（段階表の最後の段階）まで管理する。段階の定義は `ai-docs/env/task-workflow.md`、案件固有の事情は `.claude/workspace.md` だけを正とし、このコマンドには書き写さない。

## 行動原則

- 1段階終えたら、止まらずに次の段階へ進む。止まるのは「止まる所」に挙げた場面だけ
- 段階ごとの報告は5行以内
- 手順・規約・決まりを述べるときは、根拠のファイルと行番号を添える。根拠が無いものは「未確認」と書き、決まりとして扱わない
- 段階表の段階を飛ばさない。飛ばしたいときはユーザーに確認する
- ai-docs に書くのは、ユーザーと決めたことと、コード・コマンド結果・原文で確かめた事実だけ。記録するかどうかは自分で判断し、承認を求めずに書いて報告する（`ai-docs` スキルの手順に従う）

## 止まる所

次の場面だけ AskUserQuestion で止まり、答えを得たら続ける。
- 設計判断とブランチ名の決定
- 要件の原文から決められないこと（範囲・期限・対象の食い違いなど）
- チェックの違反を自分で直せないとき
- コミット・push・PR 作成など、外に出る操作の直前（各リポジトリのスキルの許可ルールに従う）
- ユーザーの手元で確かめる必要があるとき（実機・シミュレータでの動作確認など）

## 文書の書き方

設計判断の一覧・実装計画書・ai-docs の記録は、`~/.claude/assets/feature-test/functional-test/SKILL.md` の次の節に従って簡潔に書く。書いた後に、この節に照らして読み直してから出す。
- 「PR レビュー文脈の排除」「重複表現の禁止」「言い直しの禁止」「括弧の使い分け」「『該当なし』を書かない」「平易な日本語で書く」「セル内分岐の禁止」

## 場面ごとに使う道具

次の場面では、自己流で進めずに対応する道具を使う。明示起動専用のコマンドは、ファイルを Read してその手順どおりに進める（コミット・push・PR の前は「止まる所」に従う）。
- 不具合が見つかった、期待どおりに動かない: `~/.claude/commands/c-investigate-bug.md`
- 実装する: `~/.claude/commands/c-implement.md`
- セルフレビュー: `c-review-panel` スキル
- 実装とセルフレビューの前: `ai-docs/lessons.md` を読み、当てはまる教訓に従う。使った教訓は「最終参照」を今日にする
- ユーザーから指摘を受けた: `/c-distill-lesson` の手順で教訓にする
- 命名で迷う（ブランチの slug、クラス・関数名）: masuda サブエージェント
- ユーザーが手順や概念の説明を求めた: `~/.claude/commands/c-step.md`

## Step 1: 現状の把握

次を読み、事実だけを集める。
- `.claude/workspace.md` と `ai-docs/env/task-workflow.md`
- `ai-docs/INDEX.md` のタスク表。引数や貼られた内容を title・ticket で照合して対象を決める（引数が無ければ status が 進行中 のものから。複数候補なら AskUserQuestion で選ばせる）
- 照合して INDEX に無ければ新しいタスクとして扱う。タイトル・チケット番号・要件の原文を受け取った内容から取り出し、今すぐ始めるか（進行中）後で始めるか（着手予定）を聞く。着手予定ならフォルダ作成までで止め、進行中なら最初の段階から始める
- 対象が 着手予定 か ペンディング なら、進行中に変えてから始める（ペンディングなら、待っていたものが解決したかを先に確かめる）
- 既存のタスクなら、`context.md` と `log.md` の末尾、対象リポジトリの `git -C <repo> branch --show-current`、`git -C <repo> status --short`、`git -C <repo> log -5 --oneline`、段階表の各「成果物」の有無

## Step 2: 段階の判定と記録漏れの検知

- 段階表のどの段階にいるかを、Step 1 の事実から判定する。判定できなければ候補を挙げて AskUserQuestion で聞く
- 記録が無いことを「未完了」の根拠にしない。各段階の「成果物」列にあるもの（Artifact・ファイル・ブランチ等）を開いて確かめ、確かめられない段階は済んだかを AskUserQuestion で聞く
- `context.md` の「時点」「次のアクション」が、git の状態（ブランチ・コミット・変更中のファイル）や会話と食い違っていれば、記録漏れとして指摘し、Step 3 の記録で直す

## Step 3: 段階を進めるループ

今の段階から最後の段階まで、次の a〜d を繰り返す。

a. チェック（該当する段階のものだけ。違反があれば直してから進む）
- 全段階: 起動場所がワークスペースの直下であること（リポジトリのスキルが使える状態か）
- 設計まで: 範囲・期限・対象が context.md と要件の原文（Issue・チケット・チャット）と一致しているか
- ブランチ作成: `git fetch` 後に origin の既定ブランチから切る。形式は workspace.md のリポジトリ表。slug は masuda サブエージェントに候補を出させ、ユーザーの承認後に作る
- 実装以降: 作業ブランチが既定ブランチでないこと。workspace.md の「自動で書き換わるファイル」が差分に混ざっていないこと
- 品質確認: 段階表のコマンドをユーザーが打つ形のまま実行し、出力を省略せずに結果を判定する

b. 作業: 段階表のその段階の「実行するもの」を行い、「成果物」を作る。段階に挙がっているスキル・コマンド・エージェントを使う

c. 記録: 段階の成果物と、その段階で決まったこと・確かめた事実を ai-docs に残す
1. `ai-docs/INDEX.md` と `grep -rn <キーワード> ai-docs/` で関連する既存の記述を探す
2. 既存の記述と食い違うものは、どちらが正しいかを根拠で示す。確かめられなければ記録の候補から外す
3. `ai-docs` スキルの規約で書き、`context.md` の「時点」「現状サマリ」「次のアクション」と `log.md` を更新する

d. 報告して次の段階へ

```
段階: <番号> <名前> 完了（根拠: <成果物のパスや結果>）
チェック: <問題なし／直したこと>
記録: <書いたファイル／なし>
次: <次の段階の番号と名前>
```

## Step 4: 完了

最後の段階まで終えたら、段階表の完了の手順（`status: 完了`、`tasks/_archive/` への移動、INDEX の更新、恒久的な知見の昇格）を行い、完了を1行で報告する。

## 中断するとき

ユーザーの返事待ちや作業の中断で会話が終わりそうなときは、`context.md` の「現状サマリ」「次のアクション」を最新にする。他者の返事や別タスクの完了を待つために進められないときは、status を ペンディング にし、何を待っているかを「現状サマリ」に書く。次の会話では、このコマンドの Step 1 から再開する。

## エラーハンドリング

- 段階表に無い状況（手順が決まっていない段階）: 推測で手順を作らず、決める必要があることとして AskUserQuestion で聞く
- `.claude/workspace.md` が無い: ワークスペースの直下で起動しているかを確かめる。直下で無ければ、そこで起動し直すよう1行で伝えて止める。直下なのに無ければ `/c-init-workspace` を案内して止める
