# /c-cmd-gen

Claude Codeのベストプラクティスに準拠した高品質なカスタムコマンドを生成します。

**重要**: 生成するすべてのコマンドには必ず `c-` プレフィックスを付けます。

---

## あなたの役割

あなたはClaude Codeカスタムコマンド設計の専門家です。以下の専門知識を持っています：

- **カスタムコマンドの構造**: Front Matter、指示セクション、ステップ構成
- **ツール選択**: タスクに最適なallowed-toolsの選定
- **段階的処理**: Step-by-Stepでの処理フロー設計
- **品質保証**: チェックリストやバリデーションの組み込み
- **再現性**: 誰が実行しても同じ結果を得られる設計

---

## Step 1: 要件の収集

**引数が"interactive"または空の場合**、AskUserQuestionで以下を質問：

```
Question 1: "コマンドの目的は何ですか？"
  - label: "コード品質チェック", description: "コードレビュー、リント、品質分析"
  - label: "ドキュメント生成", description: "README、API仕様書、コメント生成"
  - label: "データ処理・変換", description: "ファイル変換、データ整形、集計"
  - label: "自動化・ワークフロー", description: "複数タスクの自動実行、CI/CD連携"

Question 2: "入力データの種類は？"
  - label: "ファイル/ディレクトリパス", description: "特定のファイルやフォルダを対象"
  - label: "コードスニペット", description: "コードの一部を入力"
  - label: "テキスト/引数", description: "自由形式のテキスト"
  - label: "入力なし", description: "引数を取らない"

Question 3: "使用するツールは？"(multiSelect: true)
  - label: "Read/Write/Edit", description: "ファイル操作"
  - label: "Glob/Grep", description: "ファイル検索・コード検索"
  - label: "Bash", description: "コマンド実行"
  - label: "Task", description: "サブエージェント起動"
```

**引数が指定されている場合**、その内容から要件を分析します。

---

## Step 2: カスタムコマンド構造の設計

収集した要件に基づいて、以下の構造でコマンドを設計します：

### 2.1 Front Matter設計

```yaml
---
description: "簡潔な説明（30文字以内）"
argument-hint: "[引数のヒント]"
allowed-tools: "使用可能なツールのカンマ区切りリスト"
---
```

**allowed-toolsの選択基準**：

| タスク種別 | 推奨ツール |
|----------|-----------|
| コード分析 | Read, Grep, Glob, Task |
| ファイル操作 | Read, Write, Edit |
| コマンド実行 | Bash, Read |
| 複雑なワークフロー | Task, Read, Write, Bash |
| 対話的処理 | AskUserQuestion, Read, Write |

### 2.2 処理フローの設計

**基本パターン**：
```
Step 1: 入力の検証とパース
  ├─ 引数のバリデーション
  └─ 必要なリソースの確認

Step 2: メイン処理
  ├─ データ収集
  ├─ 分析・変換
  └─ 結果の生成

Step 3: 出力と検証
  ├─ 結果の整形
  ├─ 品質チェック
  └─ ユーザーへの報告
```

**複雑な処理の場合**：
- Taskツールを使ってサブエージェントに委譲
- 処理を並列化できる部分を特定
- エラーハンドリングを明示

### 2.3 品質保証の組み込み

各コマンドには以下を含めます：

**チェックリスト**：
- [ ] 入力が正しい形式か
- [ ] 必要なファイルが存在するか
- [ ] 処理結果が期待通りか
- [ ] エラーケースへの対応

**ベストプラクティス**：
- 明確なステップ分割
- 各ステップの目的を明記
- 中間結果の検証
- ユーザーへのフィードバック

## Step 4: 使用例とドキュメント生成

生成したコマンドと一緒に、以下の情報を提供します：

### 4.1 基本的な使用例

```bash
# パターン1: 基本的な使用
/c-コマンド名 [基本的な引数]

# パターン2: オプション付き
/c-コマンド名 [引数] --option

# パターン3: 対話モード（該当する場合）
/c-コマンド名 interactive
```

### 4.2 想定されるユースケース

**ユースケース1**: [シナリオ名]
- 状況: [どんな時に使うか]
- 実行例: `[コマンド例]`
- 期待結果: [何が得られるか]

**ユースケース2**: [シナリオ名]
- 状況: [どんな時に使うか]
- 実行例: `[コマンド例]`
- 期待結果: [何が得られるか]

### 4.3 カスタマイズポイント

コマンドをカスタマイズする際のポイント：
- [カスタマイズ箇所1]
- [カスタマイズ箇所2]
- [カスタマイズ箇所3]

## Step 5: ファイル保存

以下の形式でファイル名を提案し、保存します：

**デフォルト保存先**: `~/.claude/commands/c-[コマンド名].md`

**ファイル名の命名規則**：
- **必須**: `c-` プレフィックスを付ける
- 小文字とハイフンを使用
- 動詞で始める（例: `c-review-`, `c-generate-`, `c-check-`）
- 簡潔に（15文字以内が理想）

**例**：
- `/c-review-code` → `c-review-code.md`
- `/c-gen-docs` → `c-gen-docs.md`
- `/c-check-quality` → `c-check-quality.md`

## 品質基準

生成するカスタムコマンドは以下の基準を満たす必要があります：

### 必須要件
- [ ] Front Matterが正しく設定されている
- [ ] コマンドの目的が明確
- [ ] 処理ステップが論理的に分割されている
- [ ] allowed-toolsがタスクに適している
- [ ] エラーケースへの対応が含まれている

### 推奨要件
- [ ] 各ステップの目的が明記されている
- [ ] バリデーションが含まれている
- [ ] 使用例が提供されている
- [ ] カスタマイズポイントが説明されている
- [ ] 再現性が保証されている（同じ入力→同じ出力）

### 品質レベル

**Level 1 - 基本**：
- 動作する
- 目的が明確
- エラーが出ない

**Level 2 - 実用**：
- バリデーション付き
- エラーハンドリングあり
- ドキュメント完備

**Level 3 - プロダクション**：
- 再現性保証
- エッジケース対応
- パフォーマンス最適化
- チーム利用可能

## タスク別テンプレート

### コード品質チェック系

```yaml
allowed-tools: "Read, Glob, Grep, Task, Bash"
処理パターン:
  1. ファイル収集 (Glob)
  2. コード分析 (Task/Grep)
  3. 品質評価
  4. レポート生成
```

### ドキュメント生成系

```yaml
allowed-tools: "Read, Write, Glob, Task"
処理パターン:
  1. ソースコード読み込み (Read/Glob)
  2. 情報抽出 (Task)
  3. ドキュメント生成
  4. ファイル保存 (Write)
```

### 自動化・ワークフロー系

```yaml
allowed-tools: "Read, Write, Bash, Task"
処理パターン:
  1. 設定読み込み (Read)
  2. 並列タスク実行 (Task × 複数)
  3. 結果集約
  4. 完了報告
```

### データ処理・変換系

```yaml
allowed-tools: "Read, Write, Edit, Bash"
処理パターン:
  1. データ読み込み (Read)
  2. 変換処理
  3. バリデーション
  4. 出力 (Write)
```

## ベストプラクティス

### 1. 明確な責任範囲

コマンドは「一つのことを上手くやる」べきです：
- ✅ `/c-review-security` - セキュリティに特化
- ✅ `/c-gen-readme` - READMEのみ生成
- ❌ `/c-do-everything` - 多すぎる責任

### 2. 予測可能な動作

同じ入力には同じ出力：
- ランダム性を避ける
- 環境依存を最小化
- 副作用を明示

### 3. エラーメッセージの充実

```markdown
エラー時には以下を提供：
- 何が問題だったか
- なぜ失敗したか
- どうすれば解決できるか
```

### 4. 段階的な改善

```
v1: 最小限の機能で動作
  ↓
v2: バリデーション追加
  ↓
v3: エラーハンドリング強化
  ↓
v4: パフォーマンス最適化
```
