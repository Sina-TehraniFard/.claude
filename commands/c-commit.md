# /c-commit

作業内容を分析し、適切な粒度に分割してConventional Commitsスタイルの日本語コミットメッセージでコミットします。

---

## 核心となる哲学

**コミットは「作業ログ」ではなく「実現した事柄の単位」**

```
❌ 作業ログ思考:
  「まず設定ファイルを変えた」
  「次にクラス名を変えた」
  「それから機能を実装した」
  → 時系列の記録、レビュー者には意味不明

✅ 成果思考:
  「認証機能を追加した」
  「検索の速度を改善した」
  「バグを修正した」
  → 実現した事柄の単位、レビューしやすい
```

**なぜ重要か**：
- レビュー者が求めるのは**作業工程ではなく生成物と成果**
- マージされたコミットは**永続的に履歴に残る**
- 意味のないコミットは将来の履歴参照を汚す
- `git log` や `git bisect` で過去を調べる人のために書く

**1つのコミット = 1つの目的**：
- パッケージ変更、クラス名変更、機能実装などを1つのコミットに混ぜない
- 関連する変更（コード + テスト + ドキュメント）は同じ目的なので1つにまとめる

---

## あなたの役割

あなたはGitの専門家として、以下を行います：
- 変更内容を**機能的な単位**に分割（ファイル種別ではなく）
- 関連する変更（実装 + テスト + ドキュメント）を同一コミットに含める
- 適切なコミットタイプを選択
- 日本語で簡潔なコミットメッセージを作成
- Gitのベストプラクティスに従った安全なコミット

**重要な前提**: このコマンドを実行した時点で、ユーザーはコミット実行を許可しています。**毎回の確認は不要**です。計画を提示したら、そのまま実行に進んでください。

---

## Step 1: 変更状況の確認

以下のコマンドを**並列で**実行して現状を把握：

```bash
git status
git diff --stat
git diff --staged --stat
git log --oneline -5
```

**確認事項**：
- 未追跡ファイルの有無
- ステージング済み/未ステージングの変更
- 変更されたファイルの種類と数
- 直近のコミット履歴（スタイル参考用）

---

## Step 2: 変更内容の分析と分割方針の決定

変更内容を以下の観点で分析：

### 2.1 コミット粒度の基本原則

**✅ 推奨されるコミット単位**：

1. **機能実装とその関連ファイル**
   ```
   1つのコミットに含める:
   - 実装コード
   - その実装のテストコード
   - その実装に関するドキュメント
   - 関連する設定ファイルの変更
   ```

2. **修正とその検証**
   ```
   1つのコミットに含める:
   - バグ修正のコード
   - 修正を検証するテスト
   - 修正内容の説明（コメント/ドキュメント）
   ```

**❌ 避けるべき分割**：

```
悪い例:
- コミット1: 実装コード
- コミット2: テストコード
- コミット3: ドキュメント

理由: レビュー時に関連する変更を追うのが困難
```

### 2.2 分割の基準

**機能単位での分割**：

| 分割単位 | 含める内容 | 例 |
|---------|-----------|-----|
| 新機能追加 | 実装 + テスト + ドキュメント | ユーザー認証機能（auth.py + test_auth.py + README更新） |
| バグ修正 | 修正 + テスト + 説明 | ログインエラー修正（login.py + test_login.py + 修正コメント） |
| リファクタリング | コード整理 + テスト更新 | 認証ロジック整理（auth.py + test_auth.py） |
| 独立した設定変更 | 設定ファイルのみ | .gitignore更新、依存関係更新 |

**分割が必要な場合**：

```
以下の場合は複数のコミットに分割:

1. 複数の独立した機能/修正が含まれる場合
   例: 認証機能追加 と 検索機能追加 → 2つのコミット

2. 準備的なリファクタリングと機能追加が含まれる場合
   例: コミット1: リファクタリング
       コミット2: 新機能追加

3. 設定変更と機能変更が独立している場合
   例: コミット1: 依存関係更新
       コミット2: 新機能追加
```

### 2.3 コミットタイプの選択基準

| タイプ | 用途 | 例 |
|--------|------|-----|
| `feat` | 新機能追加 | feat: ユーザー認証機能を追加 |
| `fix` | バグ修正 | fix: ログイン時のエラーを修正 |
| `refactor` | リファクタリング | refactor: 認証ロジックを整理 |
| `style` | スタイル/フォーマット | style: コードフォーマットを統一 |
| `docs` | ドキュメントのみ | docs: READMEにセットアップ手順を追加 |
| `chore` | 雑務/設定 | chore: 依存パッケージを更新 |
| `perf` | パフォーマンス改善 | perf: クエリの実行速度を改善 |
| `test` | テストのみ追加 | test: 既存機能のテストカバレッジ向上 |

**重要**: `feat` や `fix` のコミットには、関連するテストとドキュメントを含めます。

---

## Step 3: コミットの実行

分割方針に従い、以下の手順でコミット：

### 3.1 コミット計画の提示と即時実行

以下の形式で計画を提示し、**そのまま実行に進む**（確認待ちしない）：

```
📋 コミット計画 → 実行します

1. [タイプ]: [説明]
   対象: [ファイルリスト]

2. [タイプ]: [説明]
   対象: [ファイルリスト]
```

**内部チェック**（提示不要）：
- 同じ機能に関する実装とテストが同じコミットに含まれているか
- 独立した機能/修正が別のコミットに分かれているか

### 3.2 各コミットの実行

各コミットで以下を実行：

```bash
# 1. 関連するすべてのファイルをステージング
#    （実装 + テスト + ドキュメント + 設定を一括で）
git add [実装ファイル] [テストファイル] [ドキュメント] [その他]

# 2. ステージング内容を確認
git diff --staged --stat
git diff --staged  # 必要に応じて詳細確認

# 3. コミット実行
git commit -m "$(cat <<'EOF'
[タイプ]: [日本語で簡潔な説明]
EOF
)"

# 4. コミット結果を確認
git log --oneline -1
git show --stat  # 含まれるファイルを確認
```

### 3.3 コミットメッセージのルール

**必須ルール**：
- 1行で完結（50文字以内推奨）
- `タイプ: 説明` の形式
- 説明は日本語で「〜を追加」「〜を修正」などの体言止め
- 絵文字は使用しない
- コミット本文にテストやドキュメントの含有を明示しない（当然含まれるべきなので）

**良い例**：
```
feat: ユーザー認証機能を追加
fix: カテゴリ画面でのパンくずリスト表示を修正
refactor: 認証処理をサービスクラスに分離
test: ログイン機能のテストカバレッジを向上
docs: API仕様書にエンドポイント一覧を追加
chore: package.jsonの依存関係を更新
```

**悪い例**：
```
✗ 修正しました（タイプがない）
✗ feat: Fixed the bug（日本語でない）
✗ feat: ユーザー認証機能とテストとドキュメントを追加（冗長）
✗ fix: バグ修正（何の修正か不明）
```

---

## Step 4: 完了報告

すべてのコミット完了後、以下を報告：

```
✅ コミット完了

実行したコミット:
1. [ハッシュ] [タイプ]: [説明]
   含まれるファイル: [件数]ファイル（実装・テスト・ドキュメント含む）

2. [ハッシュ] [タイプ]: [説明]
   含まれるファイル: [件数]ファイル

git log --oneline -n で確認できます
git show [ハッシュ] --stat で詳細を確認できます
```

## 重要な注意事項

### Gitセーフティプロトコル

**絶対に行わないこと**：
- `git push --force`（明示的な指示がない限り）
- `git reset --hard`（明示的な指示がない限り）
- `git config` の変更
- `--no-verify` オプションの使用
- 他の開発者のコミットの `--amend`

**必ず確認すること**：
- コミット前に `git status` で状態確認
- 機密情報（.env, credentials等）をコミットしない
- コミット後に `git log` と `git show --stat` で結果確認

### pre-commit hookへの対応

pre-commit hookでファイルが変更された場合：
1. 変更内容を確認
2. 安全な場合のみ `--amend` で追加
3. `--amend` 前に `git log -1 --format='%an %ae'` で作者確認

---

## エラーハンドリング

**変更がない場合**:
- `git status` が clean なら「コミットする変更がありません」と報告

**コンフリクトがある場合**:
- コミット前に解決が必要な旨を報告
- 解決方法をガイド

**pre-commit hookが失敗した場合**:
- エラー内容を確認
- 修正後に再度コミットを試行
- 1回のみリトライ

## ベストプラクティス

### コミット粒度の判断例

**例1: 新機能追加**
```
変更ファイル:
- src/auth.py (認証実装)
- tests/test_auth.py (認証テスト)
- README.md (認証の使い方)
- config.py (認証設定)

→ 1つのコミット: feat: ユーザー認証機能を追加
```

**例2: バグ修正**
```
変更ファイル:
- src/login.py (ログインバグ修正)
- tests/test_login.py (バグ検証テスト追加)
- docs/bugfix.md (修正内容の説明)

→ 1つのコミット: fix: ログイン時のセッションエラーを修正
```

**例3: 複数の独立した変更**
```
変更ファイル:
- src/auth.py + tests/test_auth.py (認証機能)
- src/search.py + tests/test_search.py (検索機能)

→ 2つのコミット:
   1. feat: ユーザー認証機能を追加
   2. feat: 全文検索機能を追加
```

**例4: リファクタリング + 新機能**
```
変更ファイル:
- src/base.py (既存コードの整理)
- src/new_feature.py + tests/test_new_feature.py (新機能)

→ 2つのコミット:
   1. refactor: 基底クラスを整理
   2. feat: 新機能を追加（リファクタリング後のベースを利用）
```

### レビューしやすいコミット作り

**良いコミット**：
```
git show [hash] で以下が一目でわかる:
- 何を実装/修正したか（コード）
- それがちゃんと動くことをどう確認したか（テスト）
- どう使うか/何を直したか（ドキュメント）
```

**悪いコミット**：
```
git show [hash] では実装だけ見える:
- テストは別のコミット
- ドキュメントはまた別のコミット
→ レビュー時に3つのコミットを行き来する必要がある
```

---

## 引数の扱い

**引数が指定された場合**：
- 指定された内容に関連する変更のみをコミット対象とする
- 関連するすべてのファイル（実装・テスト・ドキュメント）を含める

**引数が省略された場合**：
- すべての変更を分析
- 機能的な関連性に基づいて適切に分割してコミット
