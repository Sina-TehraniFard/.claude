# /c-commit

作業内容を分析し、適切な粒度に分割してConventional Commitsスタイルの日本語コミットメッセージでコミットします。

---

## あなたの役割

あなたはGitの専門家として、以下を行います：
- 変更内容を論理的な単位に分割
- 適切なコミットタイプを選択
- 日本語で簡潔なコミットメッセージを作成
- Gitのベストプラクティスに従った安全なコミット

---

## Step 1: 変更状況の確認

以下のコマンドを**並列で**実行して現状を把握：

```bash
git status
git diff --stat
git diff --staged --stat
git log --oneline -5
```

**確認事項**：
- 未追跡ファイルの有無
- ステージング済み/未ステージングの変更
- 変更されたファイルの種類と数
- 直近のコミット履歴（スタイル参考用）

---

## Step 2: 変更内容の分析と分割方針の決定

変更内容を以下の観点で分析：

**分割の基準**：
1. **機能単位**: 1つの機能追加/修正は1コミット
2. **ファイル種別**: 設定ファイル、スタイル、ロジックは分離可能
3. **依存関係**: 他の変更に依存しないものは先にコミット
4. **レビュー容易性**: 1コミットで差分が大きすぎないこと

**コミットタイプの選択基準**：

| タイプ | 用途 | 例 |
|--------|------|-----|
| `feat` | 新機能追加 | feat: ユーザー認証機能を追加 |
| `fix` | バグ修正 | fix: ログイン時のエラーを修正 |
| `refactor` | リファクタリング | refactor: 認証ロジックを整理 |
| `style` | スタイル/フォーマット | style: コードフォーマットを統一 |
| `docs` | ドキュメント | docs: READMEにセットアップ手順を追加 |
| `chore` | 雑務/設定 | chore: 依存パッケージを更新 |
| `perf` | パフォーマンス改善 | perf: クエリの実行速度を改善 |
| `test` | テスト | test: ログイン機能のテストを追加 |

---

## Step 3: コミットの実行

分割方針に従い、以下の手順でコミット：

### 3.1 コミット計画の提示

ユーザーに以下の形式で計画を提示：

```
📋 コミット計画

1. [タイプ]: [説明]
   対象: [ファイルリスト]

2. [タイプ]: [説明]
   対象: [ファイルリスト]

（続く場合は3以降も）
```

### 3.2 各コミットの実行

各コミットで以下を実行：

```bash
# 1. 対象ファイルをステージング
git add [ファイルパス]

# 2. ステージング内容を確認
git diff --staged --stat

# 3. コミット実行
git commit -m "$(cat <<'EOF'
[タイプ]: [日本語で簡潔な説明]
EOF
)"

# 4. コミット結果を確認
git log --oneline -1
```

### 3.3 コミットメッセージのルール

**必須ルール**：
- 1行で完結（50文字以内推奨）
- `タイプ: 説明` の形式
- 説明は日本語で「〜を追加」「〜を修正」などの体言止め
- 絵文字は使用しない

**良い例**：
```
feat: 戻るボタンに遷移元の名前を表示
fix: カテゴリ画面でのパンくずリスト表示を修正
refactor: 認証処理をサービスクラスに分離
style: CSSの目次間隔を調整
chore: package.jsonの依存関係を更新
```

**悪い例**：
```
✗ 修正しました（タイプがない）
✗ feat: Fixed the bug（日本語でない）
✗ feat: ユーザー認証機能を追加しました。ログイン、ログアウト、パスワードリセット機能を含みます。（長すぎる）
```

---

## Step 4: 完了報告

すべてのコミット完了後、以下を報告：

```
✅ コミット完了

実行したコミット:
1. [ハッシュ] [タイプ]: [説明]
2. [ハッシュ] [タイプ]: [説明]
...

git log --oneline -n で確認できます
```

---

## 重要な注意事項

### Gitセーフティプロトコル

**絶対に行わないこと**：
- `git push --force`（明示的な指示がない限り）
- `git reset --hard`（明示的な指示がない限り）
- `git config` の変更
- `--no-verify` オプションの使用
- 他の開発者のコミットの `--amend`

**必ず確認すること**：
- コミット前に `git status` で状態確認
- 機密情報（.env, credentials等）をコミットしない
- コミット後に `git log` で結果確認

### pre-commit hookへの対応

pre-commit hookでファイルが変更された場合：
1. 変更内容を確認
2. 安全な場合のみ `--amend` で追加
3. `--amend` 前に `git log -1 --format='%an %ae'` で作者確認

---

## エラーハンドリング

**変更がない場合**:
- `git status` が clean なら「コミットする変更がありません」と報告

**コンフリクトがある場合**:
- コミット前に解決が必要な旨を報告
- 解決方法をガイド

**pre-commit hookが失敗した場合**:
- エラー内容を確認
- 修正後に再度コミットを試行
- 1回のみリトライ
