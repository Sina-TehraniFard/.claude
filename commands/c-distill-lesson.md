# /c-distill-lesson

ワークスペースで受けた指摘を、次の作業で使える教訓に直してナレッジに反映する。ナレッジを増やすことではなく、次に同じ指摘を受けないことが目的。

## 行動原則

- 指摘をそのまま写さない。1件ずつ「場面 → 行動 → 理由」に直す
- 追加する前に必ず既存と照合する。似たものがあれば、新しく足さずに既存を直す
- 1件には教訓を1つだけ書く。全文を書き直さず、該当の行だけを変える
- 推測で補わない。指摘の意図が読み取れないものは AskUserQuestion で聞く
- 書き方は `/c-advance-task` の「文書の書き方」に従う
- 記録するかどうかは自分で判断し、承認を求めずに書いて報告する

## 起動のしかた

- 自動: 会話中にユーザーから指摘・訂正・不満を受けたら、その指摘への対応を終えた区切りで Step 2 以降を行う
- 手動: 引数で対象を選ぶ
  - `session`（省略時）: この会話でユーザーから受けた指摘
  - `pr <番号...>` / `pr --last <N>` / `pr --author <名前>` / `pr --since <YYYY-MM-DD>`: 対象リポジトリ（ワークスペース直下のリポジトリ。どれか分からなければ聞く）の PR のレビューコメント。条件は組み合わせてよい

## Step 1: 指摘を集める

- `session`: この会話のユーザー発言から、Claude の振る舞いへの指摘・訂正・不満を拾う。作業の指示そのものは含めない
- `pr`: 対象リポジトリで次を実行し、レビューコメントと PR へのコメントを集める
  - PR の特定: `gh pr list --state all --limit <N> [--author <名前>] [--search "created:>=<日付>"] --json number,title`
  - コメント: `gh api repos/{owner}/{repo}/pulls/<番号>/comments` と `gh pr view <番号> --json reviews,comments`
  - お礼・承認だけのコメント、PR 作成者自身の返信は外す

## Step 2: 教訓に直す

指摘ごとに、次の形に直す。

| 項目 | 書くこと |
|---|---|
| 場面 | どんなときに当てはまるか。次に同じ場面が来たと判定できる具体さで書く |
| 行動 | その場面で何をするか、何をしないか |
| 理由 | なぜそうするか。指摘の背景 |
| 例 | 元の指摘を具体例として1つだけ |

抽象度は次の2つで確かめ、満たさなければ直す。直しても満たせないものは記録しない。
- 汎用性: この教訓が当てはまる、元の指摘とは別の場面を2つ以上挙げられる。挙げられなければ具体的すぎる
- 行動の明確さ: その場面で何をすればよいかが一意に決まる。決まらなければ抽象的すぎる

## Step 3: 既存と照合する

1. `ai-docs/INDEX.md`、`ai-docs/lessons.md`、`.claude/` 配下（CLAUDE.md・workspace.md）、`~/.claude/CLAUDE.md`、`~/.claude/commands/c-advance-task.md` を、教訓の場面と行動の語で grep する
2. 似た記述ごとに、次のどれかを選ぶ
   - 変更なし: 同じことがすでに書かれている。台帳にあれば回数を+1、最終参照を今日にする
   - 更新: 同じ場面だが、今回の指摘で範囲や行動がはっきりした。該当の行だけを書き直し、回数を+1する
   - 削除: 既存の記述と矛盾し、今回の指摘が新しい合意である。古い記述を消す（decisions なら superseded にする）
   - 追加: 似た記述が無い
3. 既存の規約に書かれているのに守れていなかった場合は、教訓を足さない。その規約が守られなかった原因（読まれる場所にない、書き方が曖昧）を直す

## Step 4: 置き場所を決める

| 教訓の種類 | 置き場所 |
|---|---|
| この案件の進め方・段階の抜け | `ai-docs/env/task-workflow.md` または `.claude/workspace.md` |
| どの案件にも当てはまる進め方 | `~/.claude/commands/c-advance-task.md` などの共通コマンド（下の「共通の場所に書くとき」に従う） |
| 案件の事実・仕様・環境 | `ai-docs/context/` または `ai-docs/env/`（`ai-docs` スキルの規約） |
| 決めた方針 | `ai-docs/decisions/` |
| 案件に限らない、ユーザーの好み・進め方 | `~/.claude/CLAUDE.md` に足す案を AskUserQuestion で出す（全プロジェクトに効くため） |
| リポジトリのチーム規約（コードの書き方等） | 規約ファイルへの追記案を示すだけにする（変更には PR が要る）。台帳には載せる |
| 上のどれにも当てはまらない | `ai-docs/lessons.md`（教訓台帳） |

格上げ: 台帳の教訓を、常に読み込まれる場所（上の表の台帳以外）へ移すかを、内容で判断する。次のどれかに当てはまれば移し、台帳からは消す。
- ユーザーが「毎回」「常に」「必ず」と言った、または今後の全作業に当てはまることが明らか
- 回数が2になった（同じ指摘を2回受けた）

共通の場所に書くとき: `~/.claude/` は別の会社の端末にも同期される。会社名・案件名・リポジトリ名・業務の中身・人名を含めず、どの案件でも通じる言葉に一般化してから書く。一般化すると意味を失うものは、案件の `ai-docs/` に書く。

## Step 5: 台帳を剪定する

`ai-docs/lessons.md` を更新するたびに行う。
- 30件を超えたら、回数が少なく最終参照が古いものから見直し、30件以下にする
- 最終参照から60日たった項目は、今も当てはまるかを確かめ、当てはまらなければ消す
- 似た項目が2つ以上あれば1つにまとめる

## Step 6: 報告

回答の末尾に1行で書く。

```
📝 教訓: 追加 N / 更新 N / 削除 N / 変更なし N（行き先: <ファイル>、格上げ: <あれば>）
```

## エラーハンドリング

- 指摘の意図が読み取れない: 推測で教訓にせず、AskUserQuestion で聞く
- `gh` が認証エラー: `! gh auth login` を打つよう1行で伝えて止める
- 対象の PR にレビューコメントが無い: その旨を1行で報告して終わる
