# /c-implement

実装タスクを受け取り、コード実装から動作確認まで実行します。
**コミットは作成しません** — 完了後、ユーザーが内容を確認してからコミットできます。

**コミュニケーション**: ですます調。専門用語には簡単な説明を添え、進捗を適宜報告します。

---

## Step 1: タスクの理解

引数を確認し、以下のいずれかを判断します：

- **パターンA: Issue番号が指定された場合**
  `gh issue view {ISSUE_NUMBER} --json title,body,labels` で内容を取得して理解します
- **パターンB: テキストでタスクが説明された場合**
  引数のテキストから理解します
- **パターンC: 引数が不明確な場合**
  AskUserQuestionで確認します：何を実装してほしいか / どのファイル・機能が対象か / 完了の基準は何か

タスクを実行可能なサブタスクに分解してから着手します。

---

## Step 2: 実装

- 実装前に関連コードを調査し、既存のスタイル・パターンを踏襲する
- KISS原則：最もシンプルな実装、必要最小限の変更、過度な抽象化を避ける
- タスクの範囲が不明確な場合はAskUserQuestionで確認する：
  - 「〜の部分も変更が必要でしょうか？」
  - 「〜という理解で合っていますか？」

---

## Step 3: 動作確認（必須）

**実装が完了したら、必ず動作確認を行います。**

1. **ビルド確認**: プロジェクト構成（package.json / Cargo.toml / pom.xml / pyproject.toml 等）から適切なビルド・型チェックコマンドを判断して実行。失敗したら修正して再実行し、成功するまで繰り返す
2. **テスト実行**: プロジェクトにテストがあれば実行。失敗したら実装を修正し、通るまで繰り返す
3. **実行確認**: スクリプトや特定機能の場合、実際に実行して期待通りの結果か検証する

---

## Step 4: 完了報告

`git status` / `git diff` で変更内容を確認し、以下の形式で報告します：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  実装が完了しました
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

📋 タスク概要
  {タスクの説明}

📝 変更したファイル
  - {ファイル1}: {変更内容}
  - {ファイル2}: {変更内容}

✅ 動作確認結果
  - ビルド: 成功
  - テスト: 成功（または N/A）
  - 実行確認: {結果}

⚠️ 次のステップ
  1. 変更内容を確認してください
     git diff
  2. 問題なければコミットしてください
     git add . && git commit -m "..."
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## エラーハンドリング

```
⚠️ ビルドエラーが発生しています

エラー内容:
{エラーメッセージ}

試した対応:
- {対応1}
- {対応2}

現在の状態:
- 変更したファイル: {ファイルリスト}

```

### 依存関係の問題

```
⚠️ 依存関係に問題があります

{問題の説明}

解決策の選択肢:
1. {選択肢1}
2. {選択肢2}

どちらで進めますか？
```

## 重要な制約

### 絶対にやらないこと

- **git commit を実行しない**
- **git push を実行しない**
- 動作確認なしで完了としない
- 壊れた状態で終わらせない

### 必ずやること

- 実装前にコードベースを理解し、既存のスタイル・パターンに合わせる
- 動作確認（ビルド・テスト）を行い、失敗したら修正する
- 完了時に変更内容を報告する

### 成果物への言及ルール

**コード・コメント・ドキュメント内**には「Claude」「AI」「自動生成」「LLM」等、生成ツールへの言及を残しません（成果物にAI生成の痕跡を残さない）。ユーザーとの対話では通常どおり事実を説明して構いません。

## 最後に

**このコマンドは、実装と動作確認が完了するまで終わりではありません。**
計画や方針の提示だけで終わらせず、必ずコードを書き、ビルド/テストを通してください。
