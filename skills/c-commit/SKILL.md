# コミットスキル

作業内容を分析し、適切な粒度に分割してConventional Commitsスタイルの日本語コミットメッセージでコミットします。

---

## 核心となる哲学

**コミットは「作業ログ」ではなく「実現した事柄の単位」**

- コミット = 1つの目的（機能実装・バグ修正・リファクタリングを混ぜない）
- 関連する変更（実装 + テスト + ドキュメント）は同一コミットにまとめる
- `git log` や `git bisect` で未来の自分や他者が読むことを意識する

---

## Step 1: 変更状況の確認

以下を**並列で**実行して現状を把握する：

```bash
git status
git diff --stat
git diff --staged --stat
git log --oneline -5
```

確認事項：
- 未追跡ファイルの有無
- ステージング済み/未ステージングの変更
- 変更されたファイルの種類と数
- 直近のコミット履歴（メッセージスタイルの参考）

---

## Step 2: 変更内容の分析と分割方針の決定

### コミット粒度の基本原則

**1つのコミットに含めるもの（同じ目的に関するすべて）**：
- 実装コード
- そのテストコード
- 関連するドキュメント・設定変更

**複数コミットに分割するケース**：
1. 複数の独立した機能/修正が含まれる場合
2. 準備的なリファクタリングと機能追加が含まれる場合
3. 設定変更と機能変更が独立している場合

### コミットタイプの選択基準

| タイプ | 用途 |
|--------|------|
| `feat` | 新機能追加 |
| `fix` | バグ修正 |
| `refactor` | リファクタリング |
| `style` | スタイル/フォーマット |
| `docs` | ドキュメントのみ |
| `chore` | 雑務/設定 |
| `perf` | パフォーマンス改善 |
| `test` | テストのみ追加 |

**注意**: `feat` / `fix` のコミットには関連するテスト・ドキュメントを含める。

---

## Step 3: コミットの実行

### 3.1 コミット計画の提示と即時実行

以下の形式で計画を提示し、**そのまま実行に進む**（確認待ちしない）：

```
📋 コミット計画 → 実行します

1. [タイプ]: [説明]
   対象: [ファイルリスト]

2. [タイプ]: [説明]
   対象: [ファイルリスト]
```

### 3.2 各コミットの実行手順

```bash
# 1. 関連するすべてのファイルをステージング
git add [実装ファイル] [テストファイル] [ドキュメント] [その他]

# 2. ステージング内容を確認
git diff --staged --stat

# 3. コミット実行（HEREDOCで正確にメッセージを渡す）
git commit -m "$(cat <<'EOF'
[タイプ]: [日本語で簡潔な説明]
EOF
)"

# 4. 結果確認
git log --oneline -1
git show --stat
```

### 3.3 コミットメッセージのルール

**必須**：
- 1行で完結（50文字以内推奨）
- `タイプ: 説明` の形式
- 説明は日本語・体言止め（「〜を追加」「〜を修正」）
- 絵文字は使用しない

**良い例**：
```
feat: ユーザー認証機能を追加
fix: カテゴリ画面でのパンくずリスト表示を修正
refactor: 認証処理をサービスクラスに分離
chore: package.jsonの依存関係を更新
```

**悪い例**：
```
✗ 修正しました（タイプがない）
✗ feat: Fixed the bug（日本語でない）
✗ feat: 認証機能とテストとドキュメントを追加（冗長）
✗ fix: バグ修正（何の修正か不明）
```

---

## Step 4: 完了報告

```
✅ コミット完了

1. [ハッシュ] [タイプ]: [説明]
   [件数]ファイル変更

2. [ハッシュ] [タイプ]: [説明]
   [件数]ファイル変更
```

---

## Gitセーフティプロトコル

**絶対に行わないこと**：
- `git push --force`（明示的な指示がない限り）
- `git reset --hard`（明示的な指示がない限り）
- `git config` の変更
- `--no-verify` オプションの使用

**必ず確認すること**：
- コミット前に `git status` で状態確認
- 機密情報（.env, credentials等）をコミットしない

**pre-commit hookが失敗した場合**：
- エラー内容を確認して修正し、再コミットを試行（1回のみリトライ）

---

## エラーハンドリング

- **変更がない**: `git status` がcleanなら「コミットする変更がありません」と報告
- **コンフリクトあり**: コミット前に解決が必要な旨を報告してガイド

---

## 分割例

**例: 複数の独立した変更**
```
変更ファイル:
- src/auth.py + tests/test_auth.py（認証機能）
- src/search.py + tests/test_search.py（検索機能）

→ 2つのコミット:
   1. feat: ユーザー認証機能を追加
   2. feat: 全文検索機能を追加
```

**例: リファクタリング + 新機能**
```
変更ファイル:
- src/base.py（既存コードの整理）
- src/new_feature.py + tests/test_new_feature.py（新機能）

→ 2つのコミット:
   1. refactor: 基底クラスを整理
   2. feat: 新機能を追加
```
